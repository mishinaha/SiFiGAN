# 2026-04-17 SiFiGAN フルスクラッチ学習の記録

LibriTTS-R と VocalSet 11（straight と vibrato）を使い、ニューラルボコーダ SiFiGAN をフルスクラッチで学習した記録である。
学習は 1,000,000 ステップまで完了し、analysis-synthesis による推論の検証も行った。

関連ドキュメント：

- `doc/Prepare.md`：データ準備の詳細
- `doc/VocalSet.md`：VocalSet 1.1 の分析
- `doc/LibriTTS-R.md`：LibriTTS-R の分析

---

## 1. 動機

SiFiGAN の作者が提供している事前学習モデルは、LibriTTS-R と NUS-48E で学習されている。
しかし NUS-48E はライセンスも入手方法もはっきりしないため、同じ条件で再学習するときの再現性に問題がある。

そこで歌唱データセットを **VocalSet 1.1**（CC BY 4.0、Zenodo で公開、616 ファイル、24kHz 換算）に差し替えてフルスクラッチで学習した。
歌唱技法は `straight`（ビブラートなしの平坦な発声）と `vibrato` の 2 種類だけを使った。

VocalSet には本来 3,613 ファイル（8.8 時間）ある。
しかし、クリーンなボコーダを学習するには、呼吸音、フライ、リップトリルのような非定常的な技法は避けたい。
そのため、straight と vibrato の 616 ファイル（1.7 時間相当）に絞った。

## 2. 学習構成

| 項目 | 設定 |
|---|---|
| Generator | `sifigan` (Source-Filter 分離型、filter_network_params 3x3/5/7 resblock) |
| Discriminator | `univnet` (multi-resolution spectral + multi-period) |
| Train config | `sifigan_1000k` (1,000,000 ステップ) |
| Sample rate | 24 kHz |
| Hop size | 120 |
| Batch size | 16 |
| Optimizer | Adam (lr=2.0e-4, betas=[0.5, 0.9]) |
| LR scheduler | MultiStepLR gamma=0.5 at [200k, 400k, 600k, 800k] |
| Loss balancing | mel=45.0, reg=1.0, adv=1.0, fm=2.0 |
| Aux feats | `mcep`, `bap` |
| Signal types | `sine` (f0 type: cf0) |

データの分割は次のとおりである。

- train_no_dev：150,158（LibriTTS-R train-clean-100+360 と VocalSet の train 15 名）
- dev：5,736（LibriTTS-R dev-clean）
- eval：4,989（LibriTTS-R test-clean と VocalSet の eval 5 名）

## 3. 作業の経緯

### 3.1 pakari (packet.ai) の時期

環境は Ubuntu 24.04 のコンテナで、RTX PRO 6000 Blackwell 96GB、96 コア、1.5TB RAM、永続 NFS 98GB である。

1. **データ準備**（`run_prepare.sh`）
   - LibriTTS-R を OpenSLR からダウンロードし、tar.gz を展開した。
   - WAV を `{speaker}/{chapter}/*.wav` から `{speaker}/wav/*.wav` へ、シンボリックリンクで再配置した。
     SiFiGAN の `path_replace()` は `"wav"` を `"hdf5"` に文字列置換して出力先を決めるので、このパス構造にしておく必要がある。
   - VocalSet は Zenodo からダウンロードし、straight と vibrato だけをシンボリックリンクで配置した。
   - `sifigan-extract-features` で WORLD 分析（f0, cf0, mcep, bap）を行い、HDF5 に保存した。
   - `sifigan-compute-statistics` で正規化用の統計量を計算した。

2. **初期のトラブルと修正**
   - numpy 2.0 以降で `np.float` が削除されていたので、`extract_features.py:272` を `np.float64` に直した（commit `a354202`）。
   - 再配置用の bash の find+ln ループが極端に遅かった（10 万ファイルで 20 分以上）。Python の `os.symlink` を使う処理に書き換え、5 秒に短縮した（commit `5253cfb`）。
   - VocalSet は 44.1 kHz だが SiFiGAN は 24 kHz を前提としている。そこで soxr で事前にリサンプリングして `wav_24k/` に置き、`wav/` のシンボリックリンクをそちらに差し替えた。

3. **学習開始時の dtype エラー**
   - 学習を始めると `RuntimeError: Input type (double) and bias type (float) should be the same` が発生した。
   - 原因：`SignalGenerator.sinusoid()` と `sinusoids()` は、数値精度を保つため `torch.float64` で累積和を計算する。しかし、その結果を `float32` に戻していなかった。
   - 修正：出力に `.to(orig_dtype)` を適用し、呼び出し元の dtype に合わせた（commit `37adb0a`）。

4. **学習の実行**（tmux セッション `train` 内）
   - 6.29 it/s で約 37 時間学習し、300k ステップに達した。
   - チェックポイント（1 個 584 MiB）は NFS に保存し、手動で B2（Backblaze）にバックアップした。

5. **pakari の消滅**
   - 2026-04-15 頃、packet.ai 側の問題で、永続ストレージを含む環境全体が完全に失われた。
   - B2 に上げてあった **HDF5 の tar.gz、stats、300k までのチェックポイント**から復元できる状態だった。

### 3.2 ruthor (RunPod) への移行

環境は RunPod の RTX 5090 Pod で、RTX 5090 32GB、120 コア、944GB RAM、エフェメラル 300GB と /workspace 100GB である。

最初に作った Pod（/workspace 300GB、MooseFS）では、小さなファイルの書き込みが極端に遅い（86 files/s）ことがわかった。
そこで、エフェメラルストレージを 300GB に拡張した Pod を作り直した。

1. **復元作業**（所要時間：約 2 時間）
   - プライベートリポジトリなので SSH agent forwarding が使えず、リポジトリは rsync で転送した。
   - `uv sync --python 3.11` で venv を作り直した。
   - B2 からエフェメラルへ：`libritts_r_hdf5.tar.gz`（60GB）と `vocalset11_hdf5.tar.gz`（508MB）を展開した。
   - OpenSLR からエフェメラルへ：LibriTTS-R の WAV を再ダウンロードした（5 アーカイブ、約 40GB）。
   - Zenodo からエフェメラルへ：VocalSet11.zip をダウンロードして unzip し、soxr で 24 kHz にリサンプリングした。
   - B2 から /workspace へ：`checkpoint-300000steps.pkl`、tfevents、stats をダウンロードした。

2. **tar 展開でのつまずき**
   - 最初の試行では、シェル変数 `$DL` の展開を誤ったため、4 プロセスのうち 3 プロセスがすぐに失敗し、成功したのは 1 プロセスだけだった。
   - 続けて残りを実行したところ、ssh 接続が切れたことで、tar が stderr に出す uid/gid 警告がパイプに詰まった。その結果、プロセスが `pipe_write` 状態のまま 1 時間以上止まった。
   - 教訓：**tmux セッション内で実行し、stderr はファイルにリダイレクトする**。`tar xzf ... 2>/workspace/logs/extract.err` のように、出力を実ファイルに書き出す。
   - `--keep-old-files` は既存ファイルがあるとエラーで終了する。既存ファイルを飛ばしたいときは `--skip-old-files` を使う。

3. **PyTorch の CUDA 問題**
   - 初回は PyTorch 2.11.0+cu130 を入れたが、RTX 5090 のドライバは 12.8 までしか対応しておらず、`CUDA: False` になった。
   - 対処：`uv pip install --index-url https://download.pytorch.org/whl/cu128 torch==2.11.0 torchaudio==2.11.0` で入れ直した。
   - その後 NVML が応答しなくなったので、Pod を再起動（Stop→Start）した。エフェメラルストレージの内容は保持されたまま、GPU が使えるようになった。

4. **ストレージ性能のベンチマーク**（Pod の再起動後に実測）

   | 操作 | エフェメラル (/) | MooseFS (/workspace) |
   |---|---|---|
   | 書き込み (500KB×500) | 5,125 files/s | 86 files/s |
   | 読込 1並列 | 6,474 files/s | 178 files/s |
   | 読込 4並列 | 7,192 files/s | 1,405 files/s |
   | 読込 8並列 | 5,398 files/s | 2,610 files/s |
   | 実HDF5読込 (逐次) | 980 files/s | — |

   学習ワークロードが必要とする読み込み速度は `batch_size=16 × 6 it/s = 96 files/s` で、エフェメラルなら 10 倍以上の余裕がある。
   一方、永続の MooseFS は**小さなファイルの書き込みが 60〜90 倍遅い**ので、HDF5 の展開のような処理には向かない。
   この結果から、ネットワーク分散ファイルシステムでは、読み込みは並列度を上げれば速くなるが、書き込みは遅いままであることがわかる。

5. **チェックポイントの自動アップロード**（`checkpoint_uploader.sh`）
   - `inotifywait -m -e close_write` で `/workspace/exp/.../checkpoints/` を監視する。
   - `.pkl` の書き込みが完了したら、すぐに `aws s3 cp` で B2 に送る。
   - あわせて tfevents と train.log も sync する。
   - 取りこぼしを防ぐため、起動時にも一度同期する。
   - この仕組みにより、**Pod が落ちても、次に起動したときに B2 から復元できる**。

6. **学習の再開と完了**
   - `train.resume=300000` を指定して 300k から再開した（5.85〜6.29 it/s）。
   - 2026-04-14 22:46 に始め、2026-04-16 08:01 に完了した（300k から 1M まで、実働約 33 時間 15 分）。
   - チェックポイントは uploader が自動でアップロードした（100k ごと、合計 10 個）。

### 4.3 評価

- **完全に収束した**：800k 以降、train/mel_loss は -0.0003 しか変化しておらず、細かな調整の段階に入っている。
- **過学習は起きていない**：train と eval の差は 0.12 前後で一定である。
- **GAN の均衡は健全である**：discriminator_loss は 3.48〜3.50 で安定しており、崩壊や発散は見られない。
- **fm_loss の上昇は問題ない**：これは GAN に特有の挙動であり、mel_loss の改善と両立している限り問題にならない。

## 5. 推論の検証 (analysis-synthesis)

5 つの入力 WAV（`~/workspace/audio-samples/`）について、F0 を 0.25、0.5、0.75、1.0、1.5、2.0、4.0 倍にして analysis-synthesis を実行し、次の 3 条件で比較した。

| ラベル | モデル | F0レンジ | 出力先 |
|---|---|---|---|
| 当方デフォルト | 自家学習 1M | f0_floor=100, f0_ceil=840 (デフォルト) | `audio-samples-anasyn/` |
| 当方ワイド | 自家学習 1M | **f0_floor=10, f0_ceil=1000** | `audio-samples-anasyn-wide/` |
| 作者モデル | 事前学習 (LibriTTS-R+NUS-48E) 1M | デフォルト | `audio-samples-anasyn-author/` |

`audio-samples-anasyn/*_original_24k.wav` も並べて置いた。
これは入力音声を soxr で 24 kHz にリサンプリングしただけのファイルで、ボコーダを通していない参照音声である。

### 作者モデルの読み込みで起きた問題

- PyTorch 2.6 以降では `torch.load()` のデフォルトが `weights_only=True` に変わった。そのため、`omegaconf.listconfig.ListConfig` を含む旧形式のチェックポイント（作者モデル）を読み込もうとすると `UnpicklingError` になる。
- 修正：`anasyn.py` の `torch.load()` に `weights_only=False` を明示的に指定した（commit `a6e3813`）。

### 観察された現象

F0 が極端に高い部分や低い部分で、次の不具合がときどき発生した。

- **F0 が非常に高い場合**：音がノイズになる区間がある。
- **F0 が非常に低い場合**：F0 factor を変えても反映されず、原音の高さのまま出力される区間がある。

発生する正確な条件はわかっていない。
「F0 がある範囲の外にある」という単純な閾値の問題ではないようで、同じファイルの中でも発生する区間としない区間がある。
**作者の事前学習モデル（NUS-48E を含む）でも同じ現象が起きる**ので、原因は学習データではなく、SiFiGAN のアーキテクチャか特徴量抽出パイプラインの性質にあると推測している。

今回はこの問題には対応しないことにした。

## 6. インフラと運用で得た知見

### 6.1 ロギングと再現性

学習と前処理のすべての工程で、次の項目をログに残した。

- 実行時の **Git コミットハッシュ**をログの冒頭に記録する。
- 実行したコマンドと主なパラメータ、ファイル数とサイズ、所要時間を記録する。
- すべてのログを `/workspace/logs/` に保存し、B2 にも同期する。
- 作業の記録を `doc/` 配下の Markdown に随時追記する。

このルールは `.claude/rules/logging.md` に明文化した。

### 6.2 長時間タスクの待ち方

当初は `ScheduleWakeup` でポーリングしようとしたが、指定した秒数が守られず、コンテキストを浪費した。
そこで、**SSH 先でブロッキングするループを回し、最大 10 分でタイムアウトさせる**方法に切り替えた。
この方法は `.claude/rules/long-running-tasks.md` に明文化した。

### 6.3 分散環境でのデータバックアップ方針

| 種類 | 保存場所 | 備考 |
|---|---|---|
| HDF5 (大量小ファイル) | B2 に **tar.gz** で保存、使用時にエフェメラル展開 | 小ファイルはNFS/分散FSで重いため |
| WAV | OpenSLR/Zenodo から都度再ダウンロード | 再現性のあるソース |
| チェックポイント | 永続ストレージ + B2 (inotify 自動アップロード) | Pod 消滅対策 |
| tfevents / ログ | 同上 (チェックポイント保存時に同期) | 学習の進捗を失わないため |
| 統計ファイル | B2 に保存 | 再計算に数十分かかるため |

Pod が消えてから復元するまでの所要時間は**約 2 時間**である。
そのうち大半はデータの再ダウンロードと展開にかかる。

### 6.4 tmux セッションの使い分け

- `train`：学習本体
- `uploader`：チェックポイントの自動アップロードの監視
- `extract`（一時的）：データの展開

セッションを分けておけば、SSH が切れてもジョブは止まらず、`tmux attach` で状態を確認できる。
パイプの詰まりを防ぐため、**stderr はファイルにリダイレクトする**。

## 7. 残された課題

1. **極端な F0 でのノイズ化と F0 の固着**：SiFiGAN の構造的な問題である可能性がある。作者モデルでも再現するので、今回の学習の不備ではない。
2. **VocalSet の技法の拡張**：belt、fast_forte、long_tones などは今回は除外した。歌唱のバリエーションを広げたい場合は、特徴量を抽出し直す必要がある。
3. **学習率スケジュールの最適化**：800k 以降はほぼ横ばいで、1M は長すぎる可能性がある。600k〜800k で打ち切れば、学習時間を 20〜30% 短縮できそうである。
4. **バッチサイズの余裕**：VRAM は 32GB のうち 7.5GB しか使っておらず、batch_size=64 程度までは容易に増やせる。
   ただし GAN の均衡はバッチサイズに敏感で、学習率のスケーリングなどを調整し直す必要があるため、今回は見送った。
