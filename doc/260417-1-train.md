# 2026-04-17 SiFiGAN フルスクラッチ学習の記録

LibriTTS-R + VocalSet 11 (straight + vibrato) による SiFiGAN ニューラルボコーダのフルスクラッチ学習。
1,000,000ステップまで完走し、analysis-synthesis による推論検証まで実施した。

関連ドキュメント:
- `doc/Prepare.md` — データ準備の詳細
- `doc/VocalSet.md` — VocalSet 1.1 の分析
- `doc/LibriTTS-R.md` — LibriTTS-R の分析

---

## 1. 動機

SiFiGAN 作者提供の事前学習モデルは **LibriTTS-R + NUS-48E** で学習されている。
NUS-48E はライセンスや入手方法が不明確で、再学習の再現性に問題がある。

そこで歌唱データセット側を **VocalSet 1.1** (CC BY 4.0、Zenodo で公開、616ファイル/24kHz換算) に差し替え、
技法としては `straight` (ビブラートなし平坦) と `vibrato` の2種のみを採用してフルスクラッチ学習を行った。

VocalSet は本来3,613ファイル(8.8時間)あるが、クリーンなボコーダ学習には呼吸音・フライ・リップトリルなどの
非定常技法は避けたいため、straight と vibrato の616ファイル (1.7時間相当) に絞った。

## 2. 学習構成

| 項目 | 設定 |
|---|---|
| Generator | `sifigan` (Source-Filter 分離型、filter_network_params 3x3/5/7 resblock) |
| Discriminator | `univnet` (multi-resolution spectral + multi-period) |
| Train config | `sifigan_1000k` (1,000,000 ステップ) |
| Sample rate | 24 kHz |
| Hop size | 120 |
| Batch size | 16 |
| Optimizer | Adam (lr=2.0e-4, betas=[0.5, 0.9]) |
| LR scheduler | MultiStepLR gamma=0.5 at [200k, 400k, 600k, 800k] |
| Loss balancing | mel=45.0, reg=1.0, adv=1.0, fm=2.0 |
| Aux feats | `mcep`, `bap` |
| Signal types | `sine` (f0 type: cf0) |

データ分割:
- train_no_dev: 150,158 (LibriTTS-R train-clean-100+360 + VocalSet train 15名)
- dev: 5,736 (LibriTTS-R dev-clean)
- eval: 4,989 (LibriTTS-R test-clean + VocalSet eval 5名)

## 3. 作業経緯

### 3.1 pakari (packet.ai) 期

環境: Ubuntu 24.04 コンテナ、RTX PRO 6000 Blackwell 96GB、96c/1.5TB RAM、NFS 98GB 永続。

1. **データ準備** (`run_prepare.sh`)
   - LibriTTS-R を OpenSLR からダウンロード、tar.gz 展開
   - WAV再配置: `{speaker}/{chapter}/*.wav` → `{speaker}/wav/*.wav` (シンボリックリンク)
     ※ SiFiGAN の `path_replace()` が `"wav"` → `"hdf5"` の文字列置換を行うため、このパス構造が必須
   - VocalSet は Zenodo からダウンロード、straight/vibrato のみシンボリックリンク
   - `sifigan-extract-features` で WORLD 分析 (f0, cf0, mcep, bap) を HDF5 へ
   - `sifigan-compute-statistics` で正規化統計

2. **初期トラブルと修正**
   - `np.float` が numpy 2.0+ で削除 → `extract_features.py:272` を `np.float64` に (commit `a354202`)
   - 再配置用の bash find+ln ループが極端に遅い (10万ファイルで20分+) → Python `os.symlink` に書き換えて5秒に短縮 (commit `5253cfb`)
   - VocalSet 44.1 kHz / SiFiGAN 24 kHz 不一致 → soxr で事前リサンプリング。`wav_24k/` に格納し `wav/` のシンボリックリンクを差し替え

3. **学習開始 → dtype エラー**
   - `RuntimeError: Input type (double) and bias type (float) should be the same`
   - 原因: `SignalGenerator.sinusoid()`/`sinusoids()` が数値精度のため `torch.float64` で累積和を計算するが、結果を `float32` に戻していなかった
   - 修正: 出力を `.to(orig_dtype)` で呼び出し元の dtype に合わせる (commit `37adb0a`)

4. **学習実行** (tmux セッション `train` 内)
   - 6.29 it/s で約37時間進行、300k ステップ到達
   - チェックポイント (584 MiB × 個数) は NFS に保存、手動で B2 (Backblaze) にバックアップ

5. **pakari 消滅**
   - packet.ai の問題により永続ストレージごと完全消失 (2026-04-15 頃)
   - B2 に上げてあった **HDF5 tar.gz + stats + 300k チェックポイントまで** で復元可能な状態

### 3.2 ruthor (RunPod) 移行

環境: RunPod RTX 5090 Pod、RTX 5090 32GB、120c/944GB RAM、エフェメラル300GB + /workspace 100GB。

- 最初に作成されたPod (/workspace 300GB MooseFS) では、小ファイルの書き込み性能が極端に遅い (86 files/s)
  ことが判明。エフェメラル拡張 (300GB) したPodに作り直した

1. **復元作業** (所要: 約2時間)
   - リポジトリを rsync で転送 (プライベートリポジトリのため SSH agent forwarding が使えず)
   - `uv sync --python 3.11` で venv 再構築
   - B2 → エフェメラル: `libritts_r_hdf5.tar.gz` (60GB) + `vocalset11_hdf5.tar.gz` (508MB) 展開
   - OpenSLR → エフェメラル: LibriTTS-R WAV 再ダウンロード (5 archives, 約40GB)
   - Zenodo → エフェメラル: VocalSet11.zip → unzip → soxr で 24 kHz リサンプリング
   - B2 → /workspace: `checkpoint-300000steps.pkl` + tfevents + stats

2. **tar 展開での落とし穴**
   - 最初の試行でシェル変数 `$DL` の展開ミスにより3プロセスが即座に失敗、1プロセスのみ成功
   - 続いて残りを実行したが、**ssh 接続切断によりtar の uid/gid 警告 (stderr) がパイプブロック**
     → プロセスが `pipe_write` 状態で1時間以上フリーズ
   - 学習: **tmux セッション内で stderr をファイルへリダイレクトする**
     `tar xzf ... 2>/workspace/logs/extract.err` のように出力を物理ファイルへ
   - `--keep-old-files` は既存ファイルでエラー終了する (`--skip-old-files` が正解)

3. **PyTorch CUDA 問題**
   - 初回: PyTorch 2.11.0+cu130 なのに RTX 5090 ドライバは 12.8 対応までで `CUDA: False`
   - 対処: `uv pip install --index-url https://download.pytorch.org/whl/cu128 torch==2.11.0 torchaudio==2.11.0`
   - その後 NVML が応答しなくなり Pod 再起動 (Stop→Start)、エフェメラルは保持された状態で GPU 復活

4. **ストレージ性能ベンチマーク** (Pod再起動後に実測)

   | 操作 | エフェメラル (/) | MooseFS (/workspace) |
   |---|---|---|
   | 書き込み (500KB×500) | 5,125 files/s | 86 files/s |
   | 読込 1並列 | 6,474 files/s | 178 files/s |
   | 読込 4並列 | 7,192 files/s | 1,405 files/s |
   | 読込 8並列 | 5,398 files/s | 2,610 files/s |
   | 実HDF5読込 (逐次) | 980 files/s | — |

   学習ワークロード要求は `batch_size=16 × 6 it/s = 96 files/s`。エフェメラルは10倍以上の余裕。
   MooseFS (永続) は **小ファイル書き込みが60-90倍遅い**ため、HDF5展開などのworkloadには向かない。
   **ネットワーク分散FSは読込は並列度でカバーできるが、書き込みは遅いまま**という構造。

5. **チェックポイント自動アップロード** (`checkpoint_uploader.sh`)
   - `inotifywait -m -e close_write` で `/workspace/exp/.../checkpoints/` を監視
   - `.pkl` が書き込み完了した瞬間に B2 へ `aws s3 cp`
   - 合わせて tfevents, train.log を sync
   - 起動時に初期同期 (取りこぼし対策)
   - **Pod が落ちても次回起動時に B2 から復元可能** という設計

6. **学習再開と完走**
   - `train.resume=300000` で 300k から再開 (5.85-6.29 it/s)
   - 2026-04-14 22:46 開始 → 2026-04-16 08:01 完了 (実働約33時間15分、300k→1M)
   - チェックポイントは uploader が自動アップロード (100k ごと、合計10個)

### 4.3 評価

- **完全に収束**: 800k以降 train/mel_loss は -0.0003 しか動かず、finer tuning の段階
- **オーバーフィットなし**: train/eval ギャップは 0.12 前後で一定
- **GAN均衡は健全**: discriminator_loss が 3.48-3.50 で安定、崩壊や暴走なし
- **fm_loss 上昇は健全**: GAN特有の挙動。mel_loss 改善と両立している限り問題ない

## 5. 推論検証 (analysis-synthesis)

5つの入力 WAV (`~/workspace/audio-samples/`) に対して F0 スケーリング 0.25/0.5/0.75/1.0/1.5/2.0/4.0 倍で
analysis-synthesis を実行し、3条件で比較:

| ラベル | モデル | F0レンジ | 出力先 |
|---|---|---|---|
| 当方デフォルト | 自家学習 1M | f0_floor=100, f0_ceil=840 (デフォルト) | `audio-samples-anasyn/` |
| 当方ワイド | 自家学習 1M | **f0_floor=10, f0_ceil=1000** | `audio-samples-anasyn-wide/` |
| 作者モデル | 事前学習 (LibriTTS-R+NUS-48E) 1M | デフォルト | `audio-samples-anasyn-author/` |

`audio-samples-anasyn/*_original_24k.wav` に入力音声を soxr で 24 kHz にリサンプリングしただけのファイル
(ボコーダを通していない参照) も並置。

### 作者モデル読み込みで発生した問題

- PyTorch 2.6+ でデフォルトが `weights_only=True` に変更されたため、`omegaconf.listconfig.ListConfig`
  を含む旧形式チェックポイント (作者モデル) が `UnpicklingError` で読み込めない
- 修正: `anasyn.py` の `torch.load()` に `weights_only=False` を明示的に指定 (commit `a6e3813`)

### 観察された現象

F0の高低が極端な部分で以下の不具合が散発的に発生:
- **非常に高いF0**: ノイズ化する区間がある
- **非常に低いF0**: F0 factor の変更が反映されない (原音の高さのまま出る) 区間がある

正確な発生条件は不明。「F0がある範囲の外」という単純な閾値ではないらしく、同じファイル内でも発生する区間と
しない区間がある。**作者の事前学習モデル (NUS-48E込み) でも同様の現象が起きる**ため、
学習データ起因ではなく SiFiGAN のアーキテクチャ/特徴量抽出パイプラインの性質と推測される。

この問題は今回は対応しないこととした。

## 6. インフラ・運用で得た知見

### 6.1 ロギングと再現性

学習・前処理の全工程でロギングを徹底:
- 実行時の **Git コミットハッシュ** をログ冒頭に記録
- 実行コマンドと主要パラメータ、ファイル数・サイズ、所要時間
- すべてのログを `/workspace/logs/` に保存し、B2 にも同期
- 作業記録を `doc/` 配下の Markdown に随時追記

ルール化: `.claude/rules/logging.md` に明文化。

### 6.2 長時間タスクのポーリング

当初 `ScheduleWakeup` でポーリングしようとしたが指定秒数が守られずコンテキストを浪費。
**SSH先でブロッキングループ + 最大10分のタイムアウト** に切り替え。
`.claude/rules/long-running-tasks.md` に明文化。

### 6.3 分散環境でのデータバックアップ戦略

| 種類 | 保存場所 | 備考 |
|---|---|---|
| HDF5 (大量小ファイル) | B2 に **tar.gz** で保存、使用時にエフェメラル展開 | 小ファイルはNFS/分散FSで重いため |
| WAV | OpenSLR/Zenodo から都度再ダウンロード | 再現性のあるソース |
| チェックポイント | 永続ストレージ + B2 (inotify 自動アップロード) | Pod 消滅対策 |
| tfevents / ログ | 同上 (チェックポイント保存時に同期) | 学習の進捗を失わないため |
| 統計ファイル | B2 に保存 | 再計算に数十分かかるため |

Pod 消滅から復元までの所要時間: **約2時間**。これにはデータ再ダウンロード・展開が支配的。

### 6.4 tmux セッション分離

- `train`: 学習本体
- `uploader`: チェックポイント自動アップロード監視
- `extract` (一時): データ展開

こうすれば SSH 切断時もジョブが生き残り、`tmux attach` で確認できる。
**stderr は必ずファイルへリダイレクトする** (パイプブロック対策)。

## 7. 残課題

1. **極端F0でのノイズ/固着**: SiFiGAN の構造的な問題の可能性。作者モデルでも再現するため本学習の不備ではない
2. **VocalSet の技法拡張**: belt, fast_forte, long_tones などは今回除外。歌唱のバリエーションを広げたい場合は再抽出が必要
3. **学習率スケジュールの最適化**: 800k以降は実質プラトーで、1Mは長すぎる可能性。600k-800kで打ち切れば学習時間を20-30%短縮できそう
4. **バッチサイズの余裕**: VRAM は 7.5GB/32GB しか使っておらず、batch_size=64 程度までは容易に拡張可能。
   ただし GAN の均衡はバッチサイズに敏感で、LR scaling 等の再調整が必要なため今回は見送り
